# AGENTS.md - `sits` R package

Guidance for AI agents working in this repository. `sits` (Satellite Image Time
Series Analysis for Earth Observation Data Cubes) is a R package. 

Follow the conventions below so contributions stay consistent with the existing 
codebase. The longer human-facing rationale lives in `contributing.md`, this 
file is the operational summary for agents.

## File organization

The `R/` directory uses a strict two-tier naming scheme. **Which prefix a file
uses is determined by whether its functions are part of the public API.**

- `sits_*.R` — **public files.** Contain user-facing, exported functions 
  (`sits_classify`, `sits_cube`, `sits_bands`, …). One topic per file. For
  various cases, the name of the file matches the main function in the file
  (`sits_bbox.R` ↔ `sits_bbox()`). There are some exception, like the 
  `sits_plot.R`, which is used to overwrite behavior of plots for specific S3
  classes;
  
- `api_*.R` — **internal API files.** Contain non-exported helper functions
  grouped by domain (`api_raster.R`, `api_bbox.R`, `api_source_mpc.R`, …). These
  form the abstraction layers used by the public functions.
 
- `data.R` documents bundled datasets, `sits-package.R` is the package doc,
  `zzz.R` holds `.onLoad`/`.onAttach`, `RcppExports.R` is auto-generated never
  edit it by hand.

When adding functionality, put the exported entry point in a `sits_<topic>.R`
file and the supporting machinery in `api_<topic>.R`.

## Naming conventions

- **Public functions:** `sits_<verb_or_noun>()`, exported, snake_case.

- **Internal functions:** MUST start with a dot followed by a short domain
  prefix, snake_case. The prefix names the API the function belongs to:
  - `.classify_*` → classify API (`api_classify.R`)
  - `.raster_*`   → raster API (`api_raster.R`)
  - `.bbox_*`     → bbox API (`api_bbox.R`)
  - `.block_*`    → block API (`api_block.R`)
  - `.source_*`   → source API (`api_source*.R`)

- Internal functions are documented with roxygen `@noRd` and `@keywords internal`
  so they are not exported and produce no `man/` page.

## Internal API usage

The `api_*.R` files are not loose helpers. Together they form a layered set of
domain APIs. **Always go through the relevant API instead of touching object
internals directly**. Avoid index cube/tile fields with `$` or `[[`, do not call
`terra::` directly, do not hand-build tibbles. Use the accessors and constructors
the APIs provide. This keeps the code resilient to changes in the underlying data
structures.

Key APIs and when to use them. For example:

- **`api_raster.R` (`.raster_*`)** - the abstraction over `terra`. ALL raster I/O
  and processing (read, write, crop, reproject, extract, summarize) goes here.
  Never call `terra::` from feature code.

- **`api_cube.R` (`.cube_*`)** - operate on a data cube (a tibble of tiles).
  Use accessors like `.cube_bands()`, `.cube_labels()`, `.cube_timeline()`,
  `.cube_crs()`, `.cube_is_regular()`, `.cube_is_complete()` rather than reading
  columns directly. Cube class is resolved with `.cube_find_class()` /
  `.cube_set_class()`.

- **`api_tile.R` (`.tile_*`)** - a tile is a single row of a cube. Use
  `.tile()` to grab one, and accessors `.tile_name()`, `.tile_bands()`,
  `.tile_timeline()`, `.tile_bbox()`, `.tile_ncols()`/`.tile_nrows()`,
  `.tile_path()` to read its fields. **Iterate a cube tiles with
  `.cube_foreach_tile()` or `slider::slide*()` over rows** DO NOT USE 
  `for`/`apply`.

- **`api_conf.R` (`.conf`) + `api_check.R` (`.check_*`)** - configuration/message
  lookup and parameter validation; see the dedicated sections below.
  
These are just example. There are files not listed in the examples like
`api_band.R`, `api_source*.R`, `api_block.R` and others. Always check if the code
base if the operation you want to perform is always resolved by an existing 
function.

For example, when you need a value from a cube, tile, time series, or bbox, 
look for an existing accessor in the matching `api_*.R` before reaching into 
the structure.

## R programming model (S3)

`sits` is built on the **S3** object system with heavy use of generics.

- New API functions should be **generic** and specialized by input data type.
  Define
  `f <- function(data, ...) { .check_set_caller("f"); UseMethod("f", data) }`
  and provide methods `f.sits`, `f.raster_cube`, `f.tbl_df`, `f.default`, etc.
  See `sits_bbox.R` and `sits_bands.R` for the canonical pattern.

- Prefer generics over `if/else` on type. If you find yourself writing
  "if A do X, else do Y" based on object class, write S3 methods instead.

- **Do NOT use S4.** Never use S4 code. S4 breaks the structure of the codebase.
 
- **`torch`-based deep-learning code uses R6**, as required by the `torch`/`luz`
  packages. Follow `sits_tempcnn.R` + `api_torch.R` for that pattern only.

### Core data types (S3 classes)

- **`sits`** - Time series tibble (samples). First columns are metadata. The
  `time_series` column holds nested per-location tibbles;
 
- **`raster_cube`** - Data cube tibble. One row per tile, with a nested
  `file_info` tibble. Specializations: `vector_cube`, `probs_cube`,
  `probs_vector_cube`, `uncertainty_cube`, `class_cube`.

- **`ml_model`** — output of `sits_train()`. Carries a second class for the
  specific algorithm (`rfor_model`, `svm_model`, generic `torch_model` for 
  `torch`-based models).

A `sits` function typically takes one of these types as input and returns one of
them.

## Code style

- **Indentation: 4 leading spaces**. Match the surrounding file.

- Keep lines within ~80 columns; break long calls onto continuation lines
  aligned under the first argument (see `api_bbox.R`).
 
- Use the **tidyverse / sf / terra** stack: `dplyr` + `tidyr` for tables,
  `purrr` + `slider` for iteration over lists/tables, `lubridate` for dates,
  `sf` for vectors, `terra` for rasters
  
- Avoid the use of `apply`, `vapply`, `lapply` and friends. Try to use `purrr`
  and `slider` as much as possible
 
- **All raster operations MUST go through the sits raster API** (`api_raster.R`),
  the abstraction layer that wraps `terra`. Do not call `terra::` directly from
  feature code.
 
- There is no `.lintr` config. Follow the existing formatting by example.

## No literal values - use config + messages

The codebase keeps literals, messages, and colors out of the source.

- **Config values** live in YAML and are read with `.conf(...)`:
  - `inst/extdata/config.yml` - user-relevant (visualization/plotting).
  - `inst/extdata/config_internals.yml` - developer-only parameters.
  - Read with e.g. `.conf("view", "leaflet_megabytes")`.

- **Error / user messages** live in `inst/extdata/config_messages.yml`, read
  with `.conf("messages", "<caller>")`.

- **Colors / legends** live in `inst/extdata/config_colors.yml`.

- For new STAC catalogues, add a `config_source_<name>.yml` under
  `inst/extdata/sources/` and specialize `api_source.R` (see `api_source_mpc.R`).

## Parameter checking

- Validate inputs with the check API in `api_check.R` (`.check_*` functions:
  `.check_samples`, `.check_is_raster_cube`, `.check_na_parameter`, …).

- At the top of each exported generic, call `.check_set_caller("<fn_name>")` so
  errors reference the correct function and pull the right message key.

## Documentation

- Documentation is generated by **roxygen2** - write roxygen comment blocks above
  functions; never edit files in `man/` or `NAMESPACE` by hand. Regenerate with
  `devtools::document()`

- Public functions need `@title`, `@name`, `@description`, `@param`, `@return`,
  `@examples` (wrapped in `if (sits_run_examples()) { ... }`), and `@export`.
  Use `@rdname` to group S3 methods under one help page.

- Internal functions use `@noRd` + `@keywords internal` (no `@export`).

## Testing

- Tests use **testthat** under `tests/testthat/`, one file per topic:
  `test-<topic>.R`. Public-API tests mirror the feature name (`test-bands.R`);
  internal-API tests use the api name (`test-api_block.R`)
  
- In `sits` it is common to only test the public functions. So, for a function `sits_example()`, we 
  only test it. The internal functions it calls are tested implicitly as we use the given public 
  function. The exception is for internal functions reused in multiple places, such as bbox or others.

- Snapshot baselines live in `tests/testthat/_snaps/`

- Add tests with any substantial change. The project targets high coverage

- Keep the tests clean. DO NOT write complex tests. Try always to test group
  of operations to avoid many micro tests.

## Build / verify

- Document, then check before considering work done:
  `devtools::document()`, `devtools::test()`, and `devtools::check()`
  (or `R CMD check`). The package must remain CRAN-clean
  
- The `sits` codebase is huge and there are many tests. When implementing or
  changing a function, try to test only that function. If you run 
  `devtools::test()` directory, the operation can take hours

## Commits

- Never commit on behalf of user. Let the user verify the changes and commit the updated files.
